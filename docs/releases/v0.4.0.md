# Pi Durable Platform v0.4.0

"Agents that run on their own" (2026-10-20), on top of [v0.3.0](v0.3.0.md). Agents can now be built as custom code on
the platform's runtime, woken by schedules and webhooks (and set their own reminders), stopped for a person's approval
before chosen tools run, kept awake while their background work runs, and identified to MCP servers with a signed
token naming the person they act for. Two first-party agents, triage and a deep researcher, show what the library
does. It includes **database migrations `00021` to `00026`**: read [Upgrading](#upgrading-from-v030) first.

## Upgrading from v0.3.0

1. **Back up the platform database.**
2. **Replace both images** (the platform and the runtime, by digest) and restart. The platform applies migrations
   `00021` (MCP identity keys and per-server identity settings), `00022` (triggers and runs), `00023` (agents' recorded
   storage versions), `00024` (tool approvals), `00025` (agent-made schedules) and `00026` (agent kinds) when it starts.
   With several replicas, upgrade them together: a v0.3 replica doesn't run triggers or know approvals.
3. **The MCP identity key is created at start.** From then on, every MCP server in **proxy mode** receives an
   `MCP-Gateway-Identity` header (`sendIdentity` is on by default). Servers that ignore unknown headers are unaffected.
   For servers run outside your company, turn *Send identity* off (platform servers: platform admins; team servers: the
   team's owners and admins). `doctor` reports the signing key under `keys mcp-identity`.
4. **Agents upgrade as they wake.** An agent that was running when you upgraded keeps its v0.3 runtime until it
   hibernates or restarts. Until then it doesn't enforce tool approvals, doesn't offer the schedule tools, doesn't
   report background work and doesn't expose documents. **Set approval policies, kinds and the Schedules setting on new
   template versions after the upgrade**: upgrading an agent to a new version restarts it on the new runtime.
5. **Reachability.** Webhooks arrive at `POST /v1/hooks/{id}` and MCP servers fetch keys at
   `/.well-known/mcp-identity-jwks.json`, both on the platform's main address: if your ingress allows only some paths,
   add them. Completion callbacks are sent from the platform to the URLs teams choose (through the address guard): its
   egress must allow them, as for teams' model providers and MCP servers.
6. **New settings, all optional:** `AGENTS_BACKGROUND_MAX` (2h), `TRIGGERS_INTERVAL` (10s), `TRIGGERS_MAX_RUN_TIME`
   (30m), `TRIGGERS_MAX_CONCURRENT_RUNS` (5), `TRIGGERS_PAUSE_AFTER_FAILURES` (5), `TRIGGERS_AGENT_MAX` (20),
   `TRIGGERS_AGENT_MIN_INTERVAL` (5m), `TRIGGERS_AGENT_DAILY_RUNS` (300). See `.env.example` and the configuration
   reference.
7. **New commands:** `rotate-mcp-identity-key` and `reset-storage-version` (both audited).

**Rolling back.** v0.3.0's images work with the schema at `00026`: v0.3 ignores the new tables and columns. While rolled
back, **triggers don't fire, and template versions with tool approvals, a kind or the Schedules setting run as plain
assistants: tools that should wait for approval run without it.** Pause those agents before rolling back.
MCP servers stop receiving identity tokens. The
agents' storage is unchanged (both releases use pi-durable 1.3.0), so the upgrade check doesn't refuse v0.3 runtimes.

## Known limitations

Unchanged from [v0.3.0](v0.3.0.md#known-limitations), except these, which this release resolves: no scheduled or
event-driven work, no custom agents, no approvals, hibernation unaware of background work, and MCP servers not knowing
who calls. New or remaining:

- **Approvals guard against the model, not the caller.** An app or service account that started a run can approve
  calls in it.
- **The runtime is semi-trusted.** Code in a runtime (an author's or a tool's) holds its agent's key and all its
  agent's conversations. It can choose among its own agent's private threads when it tells the gateway which thread a
  tool call is for ([mcp-identity.md](../mcp-identity.md#threat-model)), and it can report a fake pi-durable version
  within the upgrade check's tolerance (`reset-storage-version` recovers).
- **Webhook payloads are untrusted text given to the model**, which may call the team's tools. Frame them in the
  trigger's message template, and use approvals for tools with effects ([triggers.md](../triggers.md#threat-model)).
- **A triggered run's cost** counts all the agent's usage while it ran (usage isn't tagged by thread).
- **An agent's own sleeps go through triggers.** pi-durable's wake-up API isn't released yet; reminders use the
  `schedule` tool ([hibernation.md](../hibernation.md#when-pi-durable-ships-a-wake-up-api)).
- **Stopping a thread doesn't stop its background subagents.** They end when they finish, at `AGENTS_BACKGROUND_MAX`,
  or when the agent stops.
- **Triage keeps its queue per conversation.** Point the webhook and the scheduled sweep at the same fixed thread.
- **MCP identity tokens** go only to servers in proxy mode, never to direct-mode or app-chosen servers. Open MCP Portal
  doesn't trust them yet ([what it needs](../mcp-identity.md#what-open-mcp-portal-must-add-to-trust-these-tokens)).
- The [roadmap](../roadmap.md) plans the rest; v0.5 is about files, memory and limits.

## Verifying the images and the chart

Verify the signatures with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer**
(keyless, GitHub Actions OIDC):

```sh
cosign verify ghcr.io/ncecere/pi-durable-platform@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/image.yml@refs/tags/v0.4.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify ghcr.io/ncecere/pi-durable-platform-runtime@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/image.yml@refs/tags/v0.4.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify ghcr.io/ncecere/charts/pi-durable-platform:0.4.0 \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/chart.yml@refs/tags/v0.4.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The SBOM (SPDX) and build provenance are attached to each image as attestations, and the Release carries each image's
SBOM per platform with `checksums.txt`. `pi-durable-platform version` prints `pi-durable-platform 0.4.0 (<commit>)`; the
runtime image is labelled `org.opencontainers.image.version=0.4.0`.
