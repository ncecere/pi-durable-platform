# Pi Durable Platform v0.1.0

This is Pi Durable Platform's first release (2026-10-18). Pi Durable Platform is a self-hosted console and API where teams deploy, test and manage agents built with [Pi](https://github.com/earendil-works/pi) and its [durable package](https://github.com/earendil-works/pi/tree/main/packages/durable). Each agent runs in its own runtime, keeps its state in its own PostgreSQL schema, and hibernates when idle. People don't chat with agents in the console: a team's own apps (a chat app, a support tool) reach its agents through the platform API. The full list of changes is in the [changelog](../../CHANGELOG.md), and the design in [DESIGN.md](../../DESIGN.md).

Pi Durable Platform is an independent project. It is not affiliated with or endorsed by Earendil.

v0.1.0 ships two images: the platform (one Go binary with the React web UI embedded, backed by PostgreSQL 17) and the agent runtime (Node, one agent per container). Migrations `00001` to `00016`.

## What's in it

- **Teams and roles.** Platform roles `platform_admin` and `platform_auditor`; team roles owner, admin, editor and member. Platform admins create teams and assign owners; owners and admins manage members and invites. The authorization rules are pure functions (`internal/authz`), and a test classifies every operation in `api/openapi.yaml` for every kind of caller.
- **Personal workspaces.** While platform admins have them turned on, each person who signs in gets a team of kind `personal` with themselves as its only member. Personal workspaces deploy catalog templates only. Platform admins set defaults (max agents, max running, a monthly budget) and override them per workspace, and choose whether personal workspaces may add their own model providers and MCP servers (off by default). Platform admins and auditors see a workspace, its agents, usage and audit log, but not its conversations.
- **Templates and the reviewed catalog.** Templates are versioned; each agent is pinned to a version and can move to another (upgrade or roll back), applied at its next start. Platform admins curate platform templates. Teams write their own, and submit them to the catalog; a platform admin approves or rejects the request with a note.
- **Agents.** Team editors deploy agents from templates and test them in the console. Each agent gets its own schema and database role in a separate agents database (`AGENTS_DATABASE_URL`), and a session advisory lock on its only connection makes sure only one runtime writes for it. Service accounts create **service-managed agents** by external key (`PUT /v1/teams/{team}/agents/by-key/{key}`), for example one per user of an app. Only the team's service accounts use those; owners and admins see and delete them but don't read them. `prune-agent-storage` removes storage no agent owns.
- **Launchers** (`AGENTS_LAUNCHER`). `local`: child processes of the platform, for development. `kubernetes`: one pod per agent (no service-account token, non-root, read-only root filesystem, all capabilities dropped, optional `AGENTS_RUNTIME_CLASS` such as gVisor), with its secrets in a per-agent Secret. `agent-sandbox`: a [Kubernetes Agent Sandbox](https://agent-sandbox.sigs.k8s.io) per agent, suspended when idle; or, with `AGENTS_SANDBOX_WARM_POOL`, a standby runtime claimed from a `SandboxWarmPool` and activated as the agent (`POST /activate` with the pool's activation token), so a wake skips scheduling, image pull and Node start-up.
- **Hibernation and wake.** Agents with no work in progress, no open event streams and no recent requests hibernate after `AGENTS_IDLE_TIMEOUT` (default 10 minutes): no pod, no database connection. The next request wakes them, and work in flight resumes from storage. Team members can hibernate an agent by hand (`POST /v1/agents/{id}/hibernate`).
- **Model catalog.** Platform admins add providers: OpenAI (Responses API), Anthropic (Messages API), and servers compatible with OpenAI chat completions (LiteLLM, vLLM, Ollama, OpenRouter and others), the OpenAI Responses API or the Anthropic Messages API. "Discover models" lists what a provider offers. Models are published to every team, to chosen teams, and optionally to personal workspaces. Each provider is either **proxy** (default: agents call the platform's model gateway with their own credential, and the gateway checks the model, adds the key and records usage) or **direct** (agents get the URL and key). Team owners and admins add the team's own providers and models (proxy only, through the address guard, for that team alone). Models carry input and output prices. Usage reports (`GET /v1/teams/{team}/usage`, `GET /v1/admin/usage`) sum requests and tokens per day, model, agent or team, with a cost estimate from current prices. The runtime reports usage for models the gateway doesn't see (direct providers, the default model).
- **MCP catalog.** Platform admins add remote MCP servers (Streamable HTTP) with sealed headers and publish them. The platform reads and keeps each server's tool list. A template version gives its agents servers and all or some of their tools; tools are named `mcp__<slug>__<tool>`, and more than 20 are deferred behind `tool_search`. Calls go through the gateway's MCP proxy by default, which adds the headers, refuses tools the version left out and logs each call. Teams add their own servers (proxy only, through the address guard). Apps may give an agent their own MCP servers for one thread (`mcpServers` with a message, or `PUT .../threads/{thread}/mcp-servers`), for hosts in `AGENTS_CLIENT_MCP_HOSTS` (none by default), with headers sealed until they expire.
- **Threads.** The platform keeps a record of each thread (`agent_threads`), so listing doesn't wake the agent: title, created and updated times, busy, last reply and last error, creator and participants. `GET /v1/agents/events` streams thread changes for every agent the caller may use; `GET .../threads/{thread}/events` streams one conversation's view. A thread is **shared** or **private** (chosen by its first message; private threads are visible only to the person or service account that started it, and read as not found to everyone else). The platform sets each message's author, and on shared threads of shared teams the model is told who is speaking. Messages carry their time, the model, token usage, stop reason and tool timings. Platform admins can list any agent's threads and read one conversation with a stated reason (10 to 500 characters), recorded in the team's audit log before the conversation is returned.
- **Service accounts and personal API keys.** Team service accounts with a team role and expiring keys (`pdp_sa_…`, 1 to 365 days, two active at a time for rotation). Personal API keys (`pdp_…`) act as their person.
- **OAuth Connect.** The platform is a small OAuth 2.1 authorization server, so an app can act as the person who connects it: discovery (RFC 8414 and RFC 9728), PKCE (S256, required), Client ID Metadata Documents or Dynamic Client Registration, a consent page, 1-hour access tokens and rotating 30-day refresh tokens with reuse detection, revocation, and trusted apps that skip consent. App tokens act as the person without their platform role, on the agent routes and a few read routes.
- **Audit log.** Append-only, written in the same transaction as each change. Team audit logs for editors and above, and a platform log for admins and auditors.
- **Sign-in.** OIDC (any provider), optionally limited to email domains or IdP groups (`OIDC_ALLOWED_GROUPS`), with a bootstrap admin subject. Development personas (`DEV_AUTH=true`: admin, auditor, user, alex, blair and casey), refused unless `APP_URL` is a loopback address.
- **Operations.** `pi-durable-platform doctor` checks the configuration, the production safety rules, PostgreSQL, the API key pepper and the migration state. `migrate` applies migrations under an advisory lock (`MIGRATE_ON_START` does it at start-up). `/healthz` and `/readyz`. Rate limits are counted in PostgreSQL.

## Security model

- **One enforcement point.** Clients reach agents only through the platform API, which authenticates, authorizes and proxies. Runtimes accept only their own per-agent bearer token, and never see callers' credentials.
- **Database isolation between agents.** One schema and one role per agent; an agent's role can't read another agent's schema. The agents database is separate from the platform's.
- **Agent network isolation is yours to configure.** The platform relies on Kubernetes NetworkPolicies so that agent pods take traffic from the platform only, and reach nothing but the platform's gateway, their database and (for direct-mode providers) the providers you allow. This repository ships no NetworkPolicies or manifests: write them for your cluster.
- **Address guard.** URLs that teams choose (their model providers and MCP servers) and OAuth client metadata documents are fetched through `internal/netguard`: public addresses only (team services may also use the private networks platform admins list), never loopback, link-local or cloud metadata, re-checked and pinned at every connection, no redirects, no proxy from the environment.
- **Sealed secrets.** Provider keys, MCP headers and app-supplied thread server headers are encrypted with `ENCRYPTION_KEY` (AES-256-GCM) and never returned. `ENCRYPTION_KEY_PREVIOUS` keeps old values readable during a rotation.
- **Peppered digests.** API keys, service account keys and OAuth tokens and codes are stored only as HMAC-SHA256 digests under `API_KEY_PEPPER`; `API_KEY_PEPPER_PREVIOUS` is accepted during a rotation. They are never logged.
- **Production safety.** Off a loopback `APP_URL`, the platform refuses to start with `DEV_AUTH`, an `http://` URL, or the example keys from `.env.example`.
- Agents run code from admin-approved templates only. Templates are trusted code: there is no self-service upload.

## First release

There is no previous version, so every install of v0.1.0 is a first install. Pi Durable Platform is development software. [Known limitations](#known-limitations) lists what is missing.

**Requirements.**

| Dependency | Notes |
|---|---|
| PostgreSQL | 17. Two databases: the platform's (`DATABASE_URL`) and the agents' (`AGENTS_DATABASE_URL`, whose role needs `CREATEROLE` and `CREATE` on the database). |
| OIDC provider | The only production sign-in method. Register `${APP_URL}/auth/callback` as the redirect URI. |
| TLS | `APP_URL` must be `https://` outside development. |
| Kubernetes | For the `kubernetes` and `agent-sandbox` launchers. In the agents namespace the platform needs get, list, watch, create and delete on pods; get, create, update and delete on secrets; and, for Agent Sandbox, get, list, watch, create, patch and delete on sandboxes and get, list, watch, create and delete on sandbox claims. Agent Sandbox needs its controller and CRDs installed. |
| Models | Any provider above, or the scripted `demo` model for trying it out. |

**Install.** Run `pi-durable-platform migrate` and then `serve` from the platform image, with the runtime image as `AGENTS_IMAGE`, both pinned by digest. Generate your own `ENCRYPTION_KEY` and `API_KEY_PEPPER` (`openssl rand -base64 32` each, different values), keep them in your secrets store and with your backups, and never reuse the example values. Run `pi-durable-platform doctor` to check the result. Deployment guidance is on the documentation site, <https://docs.pdp.bitop.dev>.

## Known limitations

- **One platform replica.** Rate limits, thread events and OAuth state are shared through PostgreSQL, but the idle reaper only knows the event streams open on its own replica, so another replica can hibernate an agent whose stream is open elsewhere (the client reconnects and wakes it). Several replicas have not been tested. The `local` launcher is single-process by nature.
- **Budgets are not enforced.** The personal workspace monthly budget is recorded only, and shared teams have no limits on agent count or running agents.
- **No scheduled wake-ups.** A hibernated agent wakes only on a request; work scheduled for later doesn't run while it sleeps.
- **Text only.** Messages are text (up to 32,000 characters). No files, images or artifacts, and no object storage.
- **No tool approvals.** Agents call the tools their template version allows without asking anyone.
- **Whole-view events.** Thread event streams send the whole conversation view on each change (coalesced to 10 a second), not incremental deltas.
- **Service-managed agents are service-account only.** Agents by external key can't be created by people, personal API keys or OAuth Connect apps.
- **No paging.** Thread lists and conversations come back whole.
- **OAuth Connect** doesn't support `login_hint` or `prompt=none`; the only scope is `agents`.
- **No agent transfer** between teams or workspaces.
- **Messages always queue.** A message sent while the agent is replying is handled after the reply (`whenBusy: followUp`); steering a reply in progress is not exposed.
- **Fixed runtime resources.** Agent pods request 50m CPU and 160 MiB and are limited to 1 CPU and 512 MiB; templates can't change it.
- **No re-encryption command.** Keep `ENCRYPTION_KEY_PREVIOUS` until every sealed value has been saved again under the new key.
- **No deployment manifests** in this repository (no Helm chart, Kustomize base or NetworkPolicies), no metrics endpoint, dashboards or tracing.
- **Advisory locks are database-wide**, so any role in the agents database could block another agent's lock key: acceptable for trusted templates only. Database roles are server-wide and outlive a dropped agents database.
- **Thread IDs are chosen by clients.** Use random IDs: anyone who may use an agent can set the MCP servers of a thread that doesn't exist yet, which a later private thread with that ID would inherit.
- pi-durable is experimental and pinned to 1.3.0; its storage conformance suite guards every upgrade.
- Development software: it has not run in production outside the maintainer's own installation.

## Images

| Image | What |
|---|---|
| `ghcr.io/ncecere/pi-durable-platform` | The platform (distroless, UID 65532, read-only root filesystem) |
| `ghcr.io/ncecere/pi-durable-platform-runtime` | The agent runtime (Node 22, UID 10001, read-only root filesystem with a writable `/tmp`) |

Both are tagged `v0.1.0` and `latest`, for linux/amd64 and linux/arm64. Deploy by digest. The digests are in the GitHub Release, its `<image>-v0.1.0.digest.txt` assets and the workflow's job summary:

```text
ghcr.io/ncecere/pi-durable-platform@sha256:<filled in at release>
ghcr.io/ncecere/pi-durable-platform-runtime@sha256:<filled in at release>
```

## Verifying the images

Verify the signatures with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer** (keyless, GitHub Actions OIDC). The signatures are stored in cosign v3's bundle format, so cosign v2 reports "no signatures found":

```sh
cosign verify ghcr.io/ncecere/pi-durable-platform@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/image.yml@refs/tags/v0.1.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify ghcr.io/ncecere/pi-durable-platform-runtime@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/image.yml@refs/tags/v0.1.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Each signature covers the multi-arch index, and so every tag that points at it. The SBOM (SPDX) and build provenance are attached to each image as attestations:

```sh
docker buildx imagetools inspect ghcr.io/ncecere/pi-durable-platform@sha256:<digest> --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/ncecere/pi-durable-platform@sha256:<digest> --format '{{ json .Provenance }}'
```

The Release also carries each image's SBOM per platform as `<image>-v0.1.0-linux-<arch>.sbom.spdx.json`, with `checksums.txt` (`sha256sum -c checksums.txt`). `pi-durable-platform version` in the platform image prints `pi-durable-platform 0.1.0 (<commit>)`; the runtime image is labelled `org.opencontainers.image.version=0.1.0`.
