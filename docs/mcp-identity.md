# The person behind an MCP tool call

Design note for roadmap item Z6 ([#57](https://github.com/ncecere/pi-durable-platform/issues/57)), v0.4.

## Problem

MCP servers are called with the team's credentials (the headers a platform admin or a team stored for the server) and
learn nothing about whose conversation a call is for. Servers that act for a person (their Microsoft 365 mail and
calendar, their memory) need to know which person that is, and need to be able to trust the answer.
[Open MCP Portal](https://github.com/ncecere/open-mcp-portal) already sends servers a short-lived signed identity token
for the callers it authenticates itself; calls from this platform's agents reach it (and every other server) as the
team.

## What is built

In **proxy mode** the platform's MCP gateway adds a short-lived **identity token** to every request it forwards to an
MCP server: a JWT (ES256) signed with a key only the platform holds, saying which agent is calling, for which team,
in what kind of thread, and, when the platform's own records say so, which person the call is for. Servers verify it
with the keys the platform publishes (`GET <APP_URL>/.well-known/mcp-identity-jwks.json`). The token follows Open MCP
Portal's (same header, same algorithm, same `iss`/`aud`/`exp` rules and the same `principal_type`/`sub`/`name`
claims), so a server verifies both the same way and tells them apart by `iss` and `principal_type`.

## Threat model

**What we protect.** The claim "this call is for person P". A server that trusts it may act as P: read P's mail, write
P's memory, use P's delegated credentials in the portal. A wrong claim is an impersonation.

**Who could try to make it wrong.**

| Actor | Can | Must not be able to |
|---|---|---|
| The agent's runtime and the tools it runs | Send any request to the gateway with the agent's own credential; choose the HTTP headers; be steered by the model (prompt injection through tool results, documents, messages). Today the runtime is the platform's own code, but it runs model-influenced tools, and with custom agents (#28, #29) it will run team code. So it is treated as untrusted for identity. | Name a person; make the gateway name a person the platform's records don't support; read the signing key or a token |
| An MCP server | Receive tokens meant for it, keep them, replay them | Use a token at another server; mint tokens |
| An app (OAuth Connect, service accounts) | Start threads, choose their visibility, give a thread its own MCP servers | Make the platform vouch for a person other than the one it authenticated |
| Anyone on the network | Fetch the JWKS | Forge a token |

**Rules that follow.**

1. **The gateway decides who, from its own records.** The runtime tells the gateway only *which thread* a call
   belongs to (`PDP-Thread` on its requests to the MCP proxy). The gateway looks that thread up **among the calling
   agent's threads** (the agent is authenticated by its gateway credential), and derives the person:
   - the agent belongs to a **personal workspace** → the workspace's owner;
   - otherwise the thread is **private** and was started by a **person** → that person (a private thread a service
     account started names nobody);
   - a **shared** thread, a thread the platform has no record of, or **no thread** (background work, future triggers)
     → nobody.

   The person must still be active (not suspended, not denied by the group re-check) and, for a private thread of a
   shared team, still a member of the agent's team; otherwise nobody is named. Nothing the runtime sends ever becomes
   a person, an email, a team or a visibility: those come from the database.
2. **Another agent's thread names nobody.** Thread IDs are looked up per agent, so a runtime that sends another
   agent's thread ID finds no thread of its own by that ID: the call goes on as for an unknown thread (shared, nobody).
   *Decision: no person rather than a refusal.* A thread the runtime has but the platform has no record of (threads
   older than v0.2, a record removed while a run finishes) is the same case and is legitimate; refusing would break
   those calls without protecting anything, since the outcome already names nobody. A malformed `PDP-Thread` value is
   refused (400), as it can only be a bug.
3. **The runtime never holds the key or a token.** The token is added by the gateway to the upstream request after the
   runtime's request arrives, and is not returned to the runtime. The signing key is generated by the platform and
   stored sealed with `ENCRYPTION_KEY`.
4. **Tokens are bound to one server and expire quickly.** `aud` is the server's URL (or an audience configured for the
   server); `exp` is five minutes after `iat`; every token has a `jti`. A token a server keeps is useless at another
   server and soon useless at the same one.
5. **Say little.** No thread ID (a shared thread's ID lets anyone allowed on the agent join it), no message content,
   no email unless the server is configured to receive it (default off), and no token at all for servers whose
   *Send identity* is off (for example a third party's hosted server).
6. **Never logged.** Tokens, keys and the thread header are not logged, not span attributes and not metric labels.

**Residual risk (accepted, documented).** An agent's runtime can choose *among its own agent's threads*. In a shared
team, a hostile runtime working on a shared thread could send the ID of a private thread of the same agent and get a
token naming that thread's creator. The creator chose to talk to that agent, which already holds their private
conversation and acts in it with the same tools, so this widens what the agent can do as them only to calls outside
that conversation. Today the runtime is the platform's own code, and the model can't choose the header (the runtime
sets it from the conversation the tool runs in). Before team code runs in runtimes (#29), the gateway can bind a call
to a run in progress (the thread must be busy, or the runtime presents a per-run grant the platform issued when it
relayed the message). In a personal workspace there is nothing to choose: every thread is the owner's.

## The token

Header: `{"alg": "ES256", "kid": "<key id>", "typ": "JWT"}`. An example payload, for a call from a personal
workspace's agent in a private thread, to a server that receives email:

```json
{
  "iss": "https://agents.example.com",
  "aud": "https://mail.example.com/mcp",
  "sub": "0e6a3d4c-5f1b-4f0e-9b8e-2d7c1a9f3b21",
  "principal_type": "agent",
  "name": "Mail assistant",
  "team": {"id": "6f1c…", "slug": "personal-1a2b3c4d5e6f", "kind": "personal"},
  "thread_visibility": "private",
  "person": {"iss": "https://login.example.com/application/o/pdp/", "sub": "8c41d2…", "email": "ada@example.com"},
  "person_present": true,
  "tool": "search_mail",
  "jti": "9Xq3…",
  "iat": 1792500000,
  "nbf": 1792499970,
  "exp": 1792500300
}
```

| Claim | Meaning |
|---|---|
| `iss` | The platform's `APP_URL` |
| `aud` | The server's URL exactly as configured, or the server's configured audience (`identityAudience`) |
| `sub` | The calling agent's ID (UUID). The caller is always the agent |
| `principal_type` | Always `agent`. Open MCP Portal's tokens say `user` or `service_account`, so a server that checks `principal_type` before treating `sub` as a person never mistakes an agent for one |
| `name` | The agent's name (informational: teams choose it) |
| `team` | The agent's team: `id`, `slug`, and `kind` (`team`, or `personal` for a personal workspace) |
| `thread_visibility` | `private`, `shared`, or `none` when the call belongs to no thread. An unknown thread is `shared` |
| `person` | Present only when the platform names a person (above): `iss` and `sub` are the person's OIDC issuer and subject at the platform's identity provider (stable; the portal finds the same person by them); `email` only when the server's `identityEmail` is on |
| `person_present` | `true` when the call belongs to a thread of the named person's conversation; `false` when no person is named, or a personal workspace's call belongs to no thread (work nobody is present for) |
| `tool` | On a `tools/call`, the server's own name of the tool called (one call per request); absent otherwise |
| `jti`, `iat`, `nbf`, `exp` | A unique ID; issued at; valid from 30 seconds before; valid for 5 minutes |

**Which claims to trust.** Decide on `person.iss` + `person.sub` (never on `email` or `name` alone), on
`person_present` for anything that should only happen while the person is talking to the agent, and on `team.id`.
`name`, `team.slug` and `tool` are informational. A tool that needs a person refuses, with a clear message, when
`person` is absent.

**Where it arrives.** Always in **`MCP-Gateway-Identity: <jwt>`** (the bare token), never in `Authorization`, which
keeps carrying the server's own stored header (for example the team's key for the server, or a portal service
account key) unchanged. *Not chosen:* Open MCP Portal's rule (the token in `Authorization: Bearer` when the server has
no static `Authorization` header). The token is on by default for existing servers, and a public server that rejects
unknown bearer tokens would stop working on upgrade. Platform admins and teams can't store a header named
`MCP-Gateway-Identity` or `PDP-Thread`.

**Which requests.** Every request the gateway forwards to a server whose *Send identity* is on: the handshake, lists,
calls, notifications and session `GET`/`DELETE`. Each carries a fresh token. The runtime sends `PDP-Thread` with tool
calls only, so the handshake and the lists belong to no thread (`thread_visibility: none`): they name a personal
workspace's owner with `person_present: false`, and nobody otherwise. The platform's own reads of a server's tools
(create, refresh) carry no token. When the gateway can't sign (no usable key, for example after `ENCRYPTION_KEY`
changed without `ENCRYPTION_KEY_PREVIOUS`), it refuses the request (503 `identity_unavailable`) rather than send it
without the token, and logs why (never a token or a key).

## Keys and rotation

- **Generated by the platform.** The first time a token is needed (and when `serve` starts) the platform creates a
  P-256 key if there is none, under a database lock so replicas make one. The private key is stored sealed with
  `ENCRYPTION_KEY` (`mcp_identity_keys.private_key_enc`, associated data `mcp_identity_key:<id>`), re-sealed by
  `rekey` like every other secret. The `kid` is the key's RFC 7638 thumbprint.
- **Which key signs.** Each key has `signs_from`. The key that signs is the one with the latest `signs_from` that has
  passed; every replica chooses by time from the same rows (cached for a minute), so they switch together.
- **The JWKS** lists the key that signs now, keys that will sign (published before they are used) and keys that
  stopped signing in the last hour (tokens last five minutes), as `application/jwk-set+json` with
  `Cache-Control: public, max-age=300`. Servers fetch it again when a token has a `kid` they haven't seen.
- **Rotating.** `pi-durable-platform rotate-mcp-identity-key` adds a key that starts signing after `--prepublish`
  (default 24h, at least 10 minutes), so servers' cached sets already hold it; the previous key stays published for an
  hour after it stops. `--now` signs with the new key at once (a server meets an unknown `kid` and fetches the set
  again), and `--drop-previous` (with `--now`, for a leaked key) removes every other key from the set at once. Keys
  that stopped signing more than a day ago are deleted by the next rotation. Each rotation is audited
  (`platform.mcp_identity_key_rotate`); the first key is too (`platform.mcp_identity_key_create`).
- **doctor** (`keys mcp-identity`) says which key signs and since when, warns when there is none yet (serve creates it)
  or it is older than 90 days (information only once its successor is published), fails when keys exist but none
  signs now, and counts keys waiting to sign.

## Per server

| Setting (API) | Default | Meaning |
|---|---|---|
| `sendIdentity` | on | Send the token (proxy mode). Turn it off for servers outside the company |
| `identityAudience` | none (the server's URL) | The token's `aud`, for example the portal's URL when the server is a gateway of Open MCP Portal and the portal checks one audience for all of them |
| `identityEmail` | off | Include the person's email in `person` |

They apply to platform servers (platform admins) and teams' own servers (their owners and admins; teams' servers are
proxy-only). Changes are audited with the server's other settings.

**Direct mode gets no token.** In direct mode the runtime calls the server itself, so the gateway never sees the
request and can't vouch for it. Handing the runtime tokens to attach would give it exactly what rule 1 forbids: a
signed statement it can present for any thread or none. A server that needs to know the person must be in proxy
mode.

**App servers** (an app's own servers for one thread, `mcpServers`) get no token: the app chose that server and
already knows its user, and an app-chosen URL shouldn't receive the platform's statement about who people are.

## For MCP server authors

1. Read `MCP-Gateway-Identity`. Without it, the call didn't come through the platform's gateway with *Send identity*
   on: treat it as anonymous.
2. Verify: `alg` is `ES256`, the `kid` is in `<APP_URL>/.well-known/mcp-identity-jwks.json` (cache it for up to five
   minutes, fetch again for an unknown `kid`), `iss` is the platform's `APP_URL`, `aud` is your URL as configured in the
   platform (or the audience configured for you), `exp`/`nbf` hold (allow 30 seconds of skew). Require
   `principal_type == "agent"`.
3. Find the person by `person.iss` + `person.sub`. No `person`: refuse tools that act for someone, with a message such
   as "This tool needs a person: use it from a personal workspace or a private thread". Check `person_present` for
   actions that need the person there (sending mail, for instance).

The verification code in Open MCP Portal's `docs/upstream-identity.md` (Go, Python, TypeScript) works unchanged with
the platform's JWKS URL and issuer; read `person` instead of `email`/`sub` for the person.

## What Open MCP Portal must add to trust these tokens

A description only; nothing here changes the portal.

- **A trusted issuer.** A portal setting (platform admins) naming the platform's `iss` and its JWKS URL, and the
  audience the portal expects (its own `APP_URL`, which the platform's servers set as `identityAudience`, or each
  gateway's URL).
- **Accept the token as the caller's identity** on `/mcp/{gateway}` requests that are authenticated as a team service
  account (the key the platform stores in the server's `Authorization` header) and carry `MCP-Gateway-Identity`
  signed by the trusted issuer, with `principal_type: agent` and a `person`. The portal finds the person by
  `person.iss` + `person.sub` (both products sign people in with the same identity provider), checks that they are
  active, and then applies that person's rules and delegated credentials (`MCP-Gateway-Provider-Token`) instead of the
  service account's. Without `person`, the call stays the service account's.
- **Who may assert people.** Only service accounts marked as the platform's (or their team) may present such tokens,
  so another team's script can't relay a platform token it obtained. The token's short life and `aud` limit replay.
- **Consent can't happen in an agent call.** A capability that needs the person to connect an account first should
  fail with a tool error that says so (the person connects in the portal), rather than `-32042` with a link nobody will
  open. `person_present: false` calls should never start a consent flow.
- **Downstream.** The portal mints its own token for the server behind it, as today (`principal_type: user` for the
  person), and should record that the call came through the platform's agent (`sub`, `name`), for example as a `via`
  or `act` claim and in its call log.

## Open questions

- Personal workspace work with no thread (future schedules, #15) names the owner with `person_present: false`. Should
  triggers' runs name nobody even in a personal workspace? The `person_present` claim lets servers decide today.
- Binding a call to a run in progress (residual risk above) before team code runs in runtimes (#29).
- Whether app servers should be able to opt in to the token.
- Whether the platform's own tool-list reads should carry a token (`principal_type: platform`) for servers that refuse
  every request without one.
